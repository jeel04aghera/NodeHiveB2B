# Engineering Foundation — `nodehive/gpu-platform`

This is the canonical onboarding doc for the V1 build. It ties together the real
artifacts in this repo (proto, SQL, Go interfaces, configs) and supplies the
rationale, contracts, and ticket plan they can't carry on their own. Read it once
top-to-bottom, then start at **Task 11 → ticket T-001**.

Scope guardrails (do not violate without a written decision): **no marketplace,
no custom scheduler, no custom overlay, no multi-region/HA, single org per
deployment.** Every component below maps to a V1 customer outcome: *see utilization
→ reclaim idle → self-serve launch → chargeback.*

```
│   └── updater/             ○ signed self-update + rollback (T-025)
├── proto/{agent,node,metrics,workload}/v1/   ● gRPC contracts

├── scripts/                 ● seed_dev.sql, dev tooling
├── deploy/                  ● docker-compose, install scripts
└── docs/                    ● this file + security packet (T-030)
```

| Directory | Purpose | Ownership | Rules |
|---|---|---|---|
| `cmd/` | Process entrypoints only | Whoever owns the binary | Thin `main`: parse config, wire deps, start. **No business logic.** |
| `internal/<module>/` | One bounded context each | Control-plane team | A module exposes a `Service` interface; cross-module calls go through interfaces, never direct table access. Owns only its tables. |
| `internal/db/queries/` | Hand-written SQL | Module author | One file per module; `sqlc generate` turns these into typed Go. No ORM. |
| `internal/db/sqlc/`, `gen/` | Generated code | Nobody (tooling) | Never edit by hand; never lint; regenerated by `make generate`. |
| `internal/platform/` | Cross-cutting infra (config, events, db pool, logging) | Platform/SRE | No domain knowledge here. |
| `agent/<pkg>/` | Agent-only packages | Agent team | Must compile and run on a customer node; no control-plane imports. Each package is one testable interface. |
| `proto/` | The agent↔server contract | Shared (review required) | Backward-compatible changes only; bump nothing without `buf breaking` passing. |
| `web/` | Frontend | Frontend team | Calls the REST API only (never the DB/gRPC). Server state via TanStack Query. |
| `migrations/` | Schema evolution | Control-plane team | Forward-only, append new files; never edit a merged migration. |
| `deploy/`, `scripts/` | Run/operate locally + self-host | Platform/SRE | Keep `git clone → running` under 15 min. |
| `pkg/` | Libraries safe to import externally | Platform/SRE | Resist using it; default to `internal/`. |

## TASK 2 — Domain Model

Entities live as Go structs in [`internal/domain/domain.go`](../internal/domain/domain.go). This section is the part code can't express: invariants, lifecycles, and context boundaries.

**Bounded contexts** (= the `internal/` modules): **Identity** (orgs, users, agent trust), **Fleet** (nodes, gpus, heartbeats), **Telemetry** (metrics), **Workloads** (launch lifecycle), **Billing** (usage/cost/rates), **Audit**. Contexts never reach into each other's tables; they collaborate via `Service` interfaces and the `events.Bus`.

**Aggregate roots:** `Organization` (tenancy root), `Node` (owns its `GPU`s — GPUs are never mutated except through their node's context), `Workload` (owns its `workload_gpus` attachments), and the immutable `UsageRecord`/`CostRecord` pair (billing).

| Entity | Key invariants | Lifecycle |
|---|---|---|
| **Organization** | `slug` unique; one row in self-hosted V1 | created at deploy → mutated only via settings |
| **User** | unique `(org_id, email)`; role ∈ {admin,user} | invited/bootstrapped → active ⇄ disabled |
| **Node** | belongs to exactly one org; `last_seen_at` drives status | `offline` → `online` (agent connects) ⇄ `degraded` (missing driver/DCGM) → `offline` (missed heartbeats) → deregistered |
| **GPU** | `uuid` globally unique + stable; belongs to one node | discovered → `healthy` ⇄ `in_use`/`idle` → `unhealthy` (Xid/ECC) |
| **Workload** | references real GPUs on one node; only platform-launched workloads are auto-stoppable | `pending` → `running` → `stopping` → `stopped` \| `failed`; `stop_reason` set on exit |
| **UsageRecord** | **immutable, append-only**; `gpu_seconds ≥ 0` | inserted by metering; never updated/deleted |
| **CostRecord** | derived = usage × rate; stored, not recomputed on read | inserted when usage is priced |
| **RateCard** | one effective rate per (org, model) at a time | created/superseded via `effective_from/to` |
| **AgentHeartbeat** | disposable; short retention | inserted each heartbeat; partition dropped on age |
| **AuditLog** | append-only; never mutated | inserted on every privileged action/event |

The two state machines worth enforcing in code (and unit-testing hardest) are **Node status** and **Workload status** — illegal transitions are bugs that cause leaked GPUs or double-bills.

## TASK 3 — Database Migrations

The full DDL is [`migrations/0001_init.sql`](../migrations/0001_init.sql) (goose, forward-only). Highlights and the *why*:

**Every table carries `org_id`** even though V1 is single-org — retrofitting a tenant key is the one change that's brutally expensive later, so we pay the trivial cost now. **Telemetry is partitioned** (`gpu_metrics`, `agent_heartbeats` range-partitioned by `ts`) so retention is a partition-drop, not a mass `DELETE`. **`usage_records` is insert-only** — the immutable metering truth.

Index rationale (each index pays for a specific query, nothing speculative):
- `users(org_id,email)` unique — login lookup + uniqueness in one.
- `gpu_nodes(org_id,status)` — "show my online nodes"; `(last_seen_at)` — the offline-sweep job.
- `gpus(uuid)` unique — agent maps samples to GPUs by UUID; `(org_id,status)` — fleet view + first-fit placement.
- `workloads(org_id,status)` — active-workloads list; `(node_id)` — per-node reconcile on agent reconnect; `(project_id)` — chargeback grouping.
- `gpu_metrics(gpu_id,ts DESC)` — the time-series chart query (the hot path).
- `usage_records(project_id,period_start)` — the chargeback rollup; `(org_id,period_start)` — period reports.
- `audit_logs(org_id,ts DESC)` — "recent activity"; `(actor_type,actor_id)` — per-actor trail.

**Likely future scaling issues (documented, not solved now):**
1. **Single Postgres primary** is the ultimate ceiling — first relief is read replicas, then org-sharding (Citus). Not before real load.
2. **`gpu_metrics` cardinality** at thousands of GPUs × 15s samples → move raw samples to a columnar store (ClickHouse) while keeping rollups in PG. Trigger: ingest or dashboard latency, measured.
3. **`usage_records` growth** is unbounded by design (immutable) → monthly partitioning + archival of cold periods.
4. **Connection exhaustion** once thousands of agents + API pods connect → PgBouncer + coarse heartbeats. (Note: agents connect over gRPC to the gateway, *not* directly to PG — this is deliberate and buys headroom.)
5. **Audit hash-chaining** (if a tamper-evident trail is later required) becomes a write-serialization point → batch/Merkle it. Not in V1.

## TASK 4 — gRPC Contracts

The real definitions are in [`proto/`](../proto). Summary:

- **`node/v1`** — shared `NodeInfo`, `GpuInfo`, `Inventory`, plus `NodeStatus`/`GpuStatus` enums. Imported by the others; no service.
- **`metrics/v1`** — `GpuMetricSample`, `MetricsBatch`. No service.
- **`workload/v1`** — `WorkloadSpec`, `WorkloadStatus`, `WorkloadState`/`StopReason` enums. No service.
- **`agent/v1`** — the only **service**: `AgentService { Enroll, Connect }`.
  - `Enroll(EnrollRequest) → EnrollResponse` — one-time: token + pubkey → `node_id` + credential.
  - `Connect(stream AgentMessage) → (stream ServerMessage)` — the persistent, **agent-initiated** bidi stream. `AgentMessage` is a `oneof` of {Heartbeat, Inventory, MetricsBatch, WorkloadStatus, CommandResult}; `ServerMessage` is a `oneof` of {LaunchWorkload, StopWorkload, GetInventory, UpdateAgent} carrying a `command_id`.

Contract rules: the agent **always dials out** (no inbound RPC ever targets the agent); `ServerMessage.payload` is the **complete command allowlist** (anything else is rejected + audited); `protocol_version` is sent on enroll and the server supports N‑1 forever (you can't force-upgrade fleets you don't own). Codegen: `make generate` (buf) → `gen/go/...`; managed mode sets `go_package`.

## TASK 6 — Agent Implementation Plan

Packages (interfaces already in [`agent/`](../agent)): `discovery`, `metrics`, `executor`, `transport`, plus `updater` (T-025) and a small `agentd` supervisor in `cmd/agent`.

**Interfaces (the test seams):** `discovery.Discoverer`, `metrics.Sampler`/`Collector`, `executor.Executor`, `transport.Transport`. Each is faked in unit tests; the two that need a real machine — `metrics` (DCGM/NVML) and `executor` (containerd+CDI) — get integration tests behind a build tag, run in CI on a GPU runner (or skipped locally).

**Dependency graph** (→ = depends on):
```
cmd/agent (supervisor)
   ├──→ transport ───────────────► control plane (gRPC, outbound)
   ├──→ discovery ──┐
   ├──→ metrics ────┼──► produce AgentMessages ──► transport.Send
   └──→ executor ◄──┘ (receives LaunchWorkload/StopWorkload from transport.Recv)
```
`transport` depends on nothing in-process except the generated proto; `discovery`/`metrics`/`executor` are independent leaves the supervisor wires together. No package imports the control plane. **Test boundaries:** supervisor logic (reconnect, reconcile, command dispatch) is unit-tested with a fake `Transport` + fake `Executor`; hardware packages are integration-tested.

## TASK 7 — Backend Implementation Plan

One monolith (`cmd/controlplane`), modules under `internal/`. Each module exposes a `Service` interface (public seam) and a `Store` interface (DB access via sqlc). Modules communicate through interfaces + the in-process `events.Bus` ([`internal/platform/events`](../internal/platform/events/events.go)) — never by importing each other's stores.

| Module | Public interface | DB access (owns) | Produces | Consumes |
|---|---|---|---|---|
| `identity` | `Service`: Login, Authenticate, CreateUser, ListUsers, IssueEnrollmentToken, EnrollAgent, BootstrapAdmin | organizations, users, enrollment_tokens, agent_credentials | `node.enrolled` | — |
| `inventory` | UpsertInventory, RecordHeartbeat, SweepOffline, ListNodes, GetNode, ListGPUs, DeregisterNode | gpu_nodes, gpus, agent_heartbeats | `inventory.updated` | — |
| `telemetry` | Ingest, Utilization, FleetSummary | gpu_metrics, rollups | `metrics.ingested` | (agent MetricsBatch via gateway) |
| `policy` | EvaluateIdle, IdleReport | — (derives) | `gpu.idle_detected` | `metrics.ingested` |
| `workloads` | Launch, Stop, Get, List, UpdateStatus | workloads, workload_gpus | `workload.started`, `workload.stopped` | `gpu.idle_detected` (safe auto-stop) |
| `billing` | RecordUsage, Chargeback, SetRate, ListRates | usage_records, cost_records, rate_cards | `usage.recorded` | `workload.*`, telemetry rollups |
| `audit` | Record, Query | audit_logs | — | subscribes to all events |

**Wiring (T-002):** `main` opens a pgx pool, constructs each module's `Store` (sqlc) then `Service`, registers event subscriptions on one `Bus`, mounts `internal/http` (chi) on `HTTP_ADDR`, and starts `internal/agentgw` (gRPC) on `GRPC_ADDR`. The agent gateway translates stream messages into `inventory`/`telemetry`/`workloads` Service calls — it's the one component allowed to fan into multiple modules.

**Why events, not direct calls, for some paths:** billing and audit must react to workload/metric activity without those modules knowing about billing/audit. Synchronous in-process bus keeps it simple now and becomes the extraction seam later (swap Bus for a broker; callers unchanged).

## TASK 8 — Frontend Structure

Next.js App Router. **Routing:** a public `/login`, then an authenticated `(dashboard)` route group with a shared layout (nav + auth guard). **State:** server state via **TanStack Query** only (no Redux); the tiny bit of client state (auth token, filters) via React state/context. **API:** every call goes through [`web/lib/api-client.ts`](../web/lib/api-client.ts); data hooks live in [`web/lib/queries.ts`](../web/lib/queries.ts). Components never call `fetch` directly.

```
web/
├── app/
│   ├── layout.tsx              ● root layout + <Providers>
│   ├── providers.tsx           ● QueryClientProvider
│   ├── login/page.tsx          ○ login screen (T-006)
│   └── (dashboard)/
│       ├── layout.tsx          ○ nav + auth guard (T-013)
│       ├── page.tsx            ○ Overview: fleet summary + idle $ (T-013)
│       ├── nodes/page.tsx      ● Nodes list  (+ nodes/[id] detail)
│       ├── gpus/page.tsx       ○ GPU list + utilization (T-013)
│       ├── workloads/          ○ list, [id] detail+logs, launch form (T-017)
│       ├── reports/page.tsx    ○ chargeback + utilization export (T-022/23)
│       └── settings/page.tsx   ○ idle policy, rate cards, users (T-018)
├── components/                 ○ charts (recharts), tables, status badges, forms
└── lib/                        ● api-client.ts, queries.ts
```

**Screen → data map:** Overview→`/metrics/summary`+`/metrics/idle`; Nodes→`/nodes`; GPUs→`/gpus`+`/metrics/utilization`; Workloads→`/workloads`,`/templates`; Reports→`/reports/*`; Settings→`/org`,`/rate-cards`,`/users`. The Overview screen is the one that sells the product (utilization + idle $ at a glance) — build it well.

## TASK 9 — Local Development

Goal: **`git clone` → running system in < 15 minutes.** Infra runs in Docker; the app processes run on the host with hot reload (fastest inner loop, and it avoids needing a built proto layer inside an image during dev).

Quickstart (also in the root [`README`](../README.md)):
```bash
cp .env.example .env
docker compose -f deploy/docker-compose.yml up -d   # Postgres :5432 + Adminer :8081
make tools          # buf, sqlc, goose, golangci-lint, air (one-time)
make generate       # proto + sqlc -> gen/, internal/db/sqlc
make tidy           # pin Go deps
make migrate        # goose up
make seed           # dev org + projects + rate cards + sample fleet
make backend        # T1: control plane (HTTP :8080, gRPC :9090)
make web            # T2: Next.js (:3000)
make agent          # T3 (optional): an agent against localhost --insecure
```
**Local Postgres:** `deploy/docker-compose.yml` (volume-backed, healthchecked). **Local backend/web/agent:** `make backend|web|agent`. **Seed data:** [`scripts/seed_dev.sql`](../scripts/seed_dev.sql) — org, projects, rate cards, and a sample offline node+GPUs so the UI renders before any real agent connects; the admin user is bootstrapped by the control plane from `DEV_BOOTSTRAP_ADMIN` (default `admin@local` / `admin123`).

**Developer onboarding checklist (day one):** install Go 1.23 + Node 20 + Docker → run the quickstart → log in at `localhost:3000` → run `make agent` and watch the sample node go online → pick a ticket from Task 11 starting at the lowest unblocked ID. If `make agent` can't connect, that's the firewall/egress path — exactly the thing to get comfortable debugging early (it's risk #1 in the field).

## TASK 10 — CI/CD

Startup-simple, in [`.github/workflows/ci.yml`](../.github/workflows/ci.yml). Three jobs, all on PR + main:

- **proto** — `buf lint` + `buf breaking` (against `main`). Stops incompatible contract changes before they ship to agents you can't force-upgrade.
- **backend** — `make tools` → `make generate` → `go mod tidy` (fails if not tidy) → **migration validation** (`goose up` then full `down-to 0` against a throwaway Postgres service, proving both directions) → `make lint` (golangci-lint) → `make test` → `make build`.
- **web** — `npm ci` → `npm run lint` → `npm run build`.

**Containerization & release:** images are built from small multi-stage Dockerfiles (control plane: build with codegen, ship a static binary on distroless; agent: static binary, shipped as a binary *and* an image). Release = git tag → CI builds and pushes `controlplane` + `agent` images and publishes the **signed** agent binary (the agent self-updater verifies the signature, T-025). Migrations run as a one-shot `goose up` job before the control plane rolls. No multi-region, no blue/green in V1 — a brief maintenance window is acceptable pre-PMF. Keep secrets in GitHub Actions secrets / cloud KMS, never in the repo.

## TASK 12 — Critical Review

A Staff Engineer's honest read of this plan before anyone writes code.

**Over-engineering to watch (trim if it slows T-001→T-013):**
- *The in-process event bus* is the borderline call. It's justified (keeps billing/audit decoupled, becomes the extraction seam), but if it tempts anyone toward async complexity in V1, replace it with direct method calls — events earn their place only if they stay synchronous and dumb.
- *Four proto packages* is slightly more structure than three would need. It's cheap and aids clarity, but resist adding a fifth "just in case."
- *Partitioning telemetry on day one* adds operational surface (the partition job). Defensible because retention-by-drop is the alternative to painful mass-DELETEs, but a single team must own the partition job or it rots.

**Missing pieces to close early (not yet ticketed in depth):**
- **Workload networking reachability** beyond "LAN IP:port + document Tailscale" is hand-waved. The first NAT'd pilot will force a real answer in T-016 — pre-validate with a design partner's network.
- **Connection/backpressure limits** on the agent gateway (how many streams, metrics flood control) — add to T-003/T-010 before the first multi-node site.
- **DB backup/restore runbook** — implied in T-027 but make it explicit; losing `usage_records` is losing money.
- **No load/perf test** in the first 30 tickets. Acceptable for PMF, but add a synthetic "1k fake agents" harness before the first 10-node customer.

**Dangerous assumptions (write them down so they're falsifiable):**
1. *Agents can dial out on 443 from customer GPU nodes.* If false, the whole model stalls — test in T-004 against a deliberately locked-down node.
2. *Customers will install a root-capable agent.* The single biggest non-technical risk; T-026's least-priv + auditability (and open-sourcing the agent) is the mitigation, not an afterthought.
3. *DCGM is present (or NVML suffices) across customer hardware.* Driver/MIG variance will surface in T-007/T-009; keep a fallback path.
4. *First-fit placement is "good enough."* True for single-org, low-contention V1; it is **not** a scheduler and must not grow into one (that's KAI/DRA's job later).
5. *Idle auto-stop is safe.* Only because we restrict it to platform-launched workloads. If anyone widens it to arbitrary processes, that's a customer-trust incident waiting to happen.

**Technical debt intentionally accepted (and the payoff condition):**
- Single Postgres, single region, no HA — accepted until a signed SLA demands otherwise.
- Hot-reload dev instead of full-compose app images — accepted; revisit if onboarding breaks the 15-min goal.
- Bearer token in memory/localStorage on the frontend — accepted for V1; move to httpOnly cookies before the first security review.
- Minimal RBAC (admin/user) — accepted; SSO/SCIM via WorkOS only when an enterprise deal requires it.
- No double-entry ledger — accepted; we capture immutable `usage_records` now (the expensive-to-retrofit part) and add the ledger when real money moves.
